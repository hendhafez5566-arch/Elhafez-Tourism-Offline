# Architecture boundaries and ratchet

Future direction: UI → Application/use cases → Domain/business rules → Repository interfaces → Persistence/infrastructure. No production layer migration in Phase 1.

ARCH001: DB identifier references in presentation files. ARCH002: UI/Pages/Forms/Print/toast references in persistence and domain/core files. ARCH003: Auth references except src/security/** and src/bootstrap.ts. ARCH004: assignment/compound assignment/increment/decrement/delete of direct public UI/DB/Auth members, plus Object.assign/defineProperty/defineProperties and Reflect.set/defineProperty/deleteProperty targeting the root UI/DB/Auth identifier itself, after stripping casts/parentheses. ARCH005: corresponding window/globalThis mutations in src/**. ARCH006: upward named-global dependencies; persistence to Accounting/Commercial/CRM/UmrahCore_Ops/Actions/UI/Pages/Forms/Print/toast, domain/core to Actions/CommercialActions/UIDelegatedActions/UI/Pages/Forms/Print/toast. Overlap of ARCH002 and ARCH006 is intentional. Ordinary window reads and as-any casts are not ARCH004/ARCH006.

Classifier: src/ui/** and files ending pages/forms/forms-contracts/view/actions-print.ts plus core/umrah/ui.ts are presentation; src/persistence/** persistence; security/** security; accounting/finance/crm/commercial/core otherwise domain-core; bootstrap exempt auth location; other source application/platform. Mixed-purpose legacy files remain classified by this explicit convention. Full implementation is in scripts/architecture-check.mjs, with actual evidence/signatures in architecture-baseline.json.

Read-only AST scanner uses TypeScript syntax, excludes comments and string contents from identifier references, and hashes printer-normalized occurrence nodes without line numbers. Multiset matching keys rule + file + signature; repeated identical findings retain multiplicity. Thus new files, increased existing-file counts, new patches and same-count replacement by a different occurrence are rejected; unchanged findings and removals pass. No automatic baseline rewrite.

Limitations: module none and manual ordering preclude a complete import graph; this measures named global syntax, not runtime reachability. It is not symbol-resolved: shadowed identifiers can be false positives; aliases, computed global names, mutations through indirect references/destructuring and arbitrary helper methods can evade detection. ARCH004 excludes nested DB.data.customer, UI.state.foo and Auth.user.name writes and mutation-helper calls targeting nested objects. Direct DB.data replacement still counts as reassignment of a public DB member. Classification of mixed core/Umrah renderers is incomplete. Signature context may flag a benign expression edit; manually review rather than automatically refresh baseline. Server imports are inventoried but rules target legacy src globals, not an exhaustive server architectural graph.

Corrective pass: CRM and commercial share the existing domain-core ARCH002/ARCH006 checks; presentation exceptions retain precedence. ARCH001/003/005 meanings and forbidden named-global sets are unchanged. Normalized identical occurrences inside one file are a multiset: counts are preserved, but deleting one and adding an identical normalized occurrence elsewhere in that same file cannot be distinguished. No claim of perfect occurrence identity. Baseline regenerated only for correction of the rule implementation; src/** is byte-identical to Phase 1 start.

Phase 2 enhancement (no baseline regeneration): src/application/** is explicitly classified as application. ARCH006 additionally rejects direct references in that new layer to DB, Auth, UI, Pages, Forms, toast, window, globalThis, document, localStorage and sessionStorage. Existing presentation/domain/persistence rules and signature matching remain unchanged. Existing bootstrap.ts is the explicit legacy port composition boundary; its deliberate wiring is inspected separately, not advertised as disappearance of all runtime globals. Application workflows receive typed ports and contain no ambient accesses.
